# Поиск автозапчастей и аналогов — Favorit-Parts

Тестовое задание: клиентское приложение на React с двухэтапным подбором номенклатуры по
Web-сервису «Проценка» (`api.favorit-parts.ru/hs/hsprice/`,
[документация](https://lk.favorit-parts.ru/static/wsprice.pdf)).

Этап 1 — вводите артикул, приложение показывает производителей этой детали.
Этап 2 — выбираете производителя, получаете аналоги и предложения с ценами и остатками.

## Быстрый старт

Нужен Node.js 18 или новее.

```bash
npm install
copy .env.example .env      # macOS/Linux: cp .env.example .env
npm run dev                 # http://localhost:5173
```

В `.env` один параметр — ключ покупателя из примеров официальной документации:

```
VITE_API_KEY=00000000-0000-0000-0000-000000000001
```

Откройте http://localhost:5173 и введите артикул, например `01089` (стеклоподъёмники),
`0189` (свечи) или `7160500039S` (опора). Появится список производителей — клик по любому
загрузит его деталь и аналоги.

Сборка и проверки:

```bash
npm run build     # production в dist/
npm run preview   # собранное приложение, прокси работает и здесь
npm test          # vitest, 10 тестов
npm run lint      # eslint, без ошибок и предупреждений
```

## Проверка

Приложение рассчитано на локальный запуск: `npm run dev`, ключ из `.env`, запросы идут через
прокси Vite — этого достаточно, чтобы посмотреть оба этапа.

Если понадобится развернуть на хостинге, одной статикой не обойтись: API не отдаёт CORS-заголовки,
поэтому нужен серверный прокси. В репозитории лежит `vercel.json` с реврайтом `/api/:path*`
и заготовка под переменную `VITE_API_KEY` — на Vercel она добавляется в настройках проекта,
`.env` в репозиторий не попадает.

### Цена берётся со складов, а не из `goods.price`

Документация прямо запрещает использовать `goods.price` («остался для совместимости, цену нужно
брать из конкретного склада»). Поэтому в `normalizeOffers` цена считается по массиву `warehouses`:

- среди складов, где `stock > 0`, берётся минимальная `price`;
- если остатка нет нигде — минимальная цена склада, а позиция помечается «нет в наличии»;
- если склады не пришли — цена `—`, приложение не падает;
- когда подходящих складов несколько, в таблице пишется «от N ₽».

Остаток — `goods.count` («остаток на всех складах»). Позиции с нулевым остатком не выбрасываются:
документация отдельно оговаривает, что такая позиция приходит и её надо показать.

### Состояния и ошибки

- `isLoading`: `''` (ещё не искали) → `pending` → `success` | `error`; каждому состоянию свой
  компонент — подсказка, `Preloader`, `ErrorMessage`, пустой результат.
- Ошибки разобраны по документации: `{ error }` в теле ответа (`Empty key!`, `Invalid key client!`,
  `Request quota exceeded!`), HTTP-ошибка с тем же полем, отсутствие ответа → сообщение о сети.
- Пустой ответ API — массив с одной пустой структурой; нормализация возвращает `[]`.
- Каждый запрос отменяется через `AbortController` при смене артикула или бренда: поздний ответ
  не перезапишет свежий, отмена не считается ошибкой.
- Пока грузится новый бренд, старая таблица остаётся под полупрозрачным лоадером — страница не
  прыгает.

### Адаптивность

Две колонки на `lg` и шире, ниже — друг под другом; таблица в `.table-responsive`, поэтому
на узком экране прокручивается горизонтально; заголовки и цены не переносятся (`text-nowrap`);
после ответа на мобильном блок предложений сам подкручивается в зону видимости.

## Ограничения

- Ключ тестовый, из примеров документации: у него есть лимит запросов (`Request quota exceeded!`).
- Ключ попадает в клиентский бандл (префикс `VITE_`) — для тестового нормально, в проде запросы
  идут через серверный прокси, и ключ остаётся на сервере.
- Дата отгрузки (`shipmentDate`) и признак невозвратной позиции (`info=on`) не выводятся:
  в задании их не требовали.
- Пагинации нет — сервис отдаёт всё сразу, аналоги сортируются по цене.
